## Notes

**Kept as the baseline** for optimization plan item S1 (self-hosted runtime mode). Compare a later run with this one only when it ran the same harness on the same runner label and CPU model, and read the spread, not single values. `results.json` next to this file has every sample, the image IDs and sizes, and the raw `jcmd GC.heap_info` output.

**Compose 2.38.2 and the shipped env file.** As the deviation line above says, Compose 2.38.2 (the version on this runner image) rejects `self-hosting/docker-compose.yml` with an env file written from `self-hosting/.env.example`, although `STORAGE_ACCESS_KEY` and `STORAGE_SECRET_KEY` are set. The workflow's probe shows why: with only `X: ${A:-${B:?need A or B}}`, A set and B unset, this Compose stops with "required variable B is missing a value" (Compose v5.5.0 renders `X: a`). The compose files read the storage keys as `${STORAGE_ACCESS_KEY:-${MINIO_ROOT_USER:?...}}`. To measure anything, the harness added `MINIO_ROOT_USER` and `MINIO_ROOT_PASSWORD` with the same values; the containers got the same credentials they would have had. Fixing the compose files is a separate change.

**Spread across runs.** One runner label gives different hardware. Two other complete runs of this harness on the same day:

| Run                                                                                        | Harness                                                          | CPU       | `GET /`   | JVM RSS idle | Visible p50 / p95 (pipelined) | Visible p50 (sequential) | transact-ok p50 |
| ------------------------------------------------------------------------------------------ | ---------------------------------------------------------------- | --------- | --------- | ------------ | ----------------------------- | ------------------------ | --------------- |
| [45169246104](https://github.com/SidekickDB/sidekick/actions/runs/45169246104) (this file) | `f2781e24`                                                       | EPYC 9V74 | 36.8 s    | 941 MiB      | 69 / 171 ms                   | 58 ms                    | 31 ms           |
| [45163785972](https://github.com/SidekickDB/sidekick/actions/runs/45163785972)             | `66d61f96` (same measurements, plus an unparsed metaspace field) | EPYC 9V45 | 32.0 s    | 936 MiB      | 53 / 100 ms                   | 44 ms                    | 24 ms           |
| [45157076682](https://github.com/SidekickDB/sidekick/actions/runs/45157076682)             | `0fa64108` (start-up timing bug, no sequential phase)            | EPYC 7763 | not valid | 940 MiB      | 589 / 722 ms                  | not run                  | 470 ms          |

Memory agrees closely across all three. Start-up differs by about 5 s between the two valid runs. The pipelined latency of the EPYC 7763 run is about ten times higher than the other two, with `transact-ok` just as high. When this note was written the harness did not show why.

**Likely cause of the EPYC 7763 result** (added later, not proven). A later run of the same harness, [45176318532](https://github.com/SidekickDB/sidekick/actions/runs/45176318532) at `bf1e8a87`, landed on an EPYC 7763 again: 5 of 5 samples, 0 missed updates, pipelined visible p50 687 ms, and sequential single-write visible p50 99 ms. That is about the 100 ms interval between pipelined writes. So on that CPU the server only just finishes one write before the next arrives, and pipelined writes most likely queue; on the EPYC 9V45 and 9V74 runs, sequential latency was 44 to 58 ms and pipelined latency stayed close to it. This fits the numbers but was not tested directly (for example with a longer write interval on the same CPU). Treat latency from a single run as indicative, compare only runs on the same CPU model, and repeat a comparison run when a result looks out of line.

**Not measured** (see `../README.md`): throughput or capacity, any workload beyond 5 WebSocket subscribers and single-entity writes, PostgreSQL internals, GC pauses, metaspace, native memory breakdown, CPU time, disk I/O, client cost, multi-node behaviour, and the Caddy or swarm variants. Image build times are from one cold build each and depend on the network.
